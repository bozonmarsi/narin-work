# Tilda-код сайта vezminarin.cz

Эти файлы не собираются и не деплоятся откуда-то — они физически вставлены
как HTML/CSS/JS-блоки в редакторе Tilda. Здесь их копия только для того,
чтобы было где посмотреть, что реально на сайте, без захода в Tilda.

**Важно:** это не источник правды в реальном времени. Если кто-то поправит
код прямо в Tilda и забудет обновить копию здесь — файлы разойдутся. При
любом следующем изменении конкретного блока: сначала возьмите текущую
версию отсюда, отредактируйте, при обновлении на сайте — обновите и файл
здесь тем же движением.

## Как это связано с supabase/

Все виджеты выше дёргают:
- `supabase/functions/personal-dates/` — даты, получатели, автопредложения из истории заказов
- `supabase/functions/member-data/` — баланс, tier, история заказов и транзакций для карты лояльности (требует `lk_auth_token`, email берётся только из токена, не из тела запроса)
- `supabase/functions/tilda-webhook/` — приём заказа из Tilda: сохраняет заказ, считает начисляемые баллы по кэшбеку текущего уровня клиента, списывает баллы по промокоду, шлёт уведомление в Telegram. Реальное зачисление баллов происходит не здесь, а триггером `handle_payment_status_change_v2` в БД, когда статус заказа меняется на "Оплачено" — webhook только записывает посчитанное значение в `tilda_orders.earned_points`. Действие `get_promo` (вызывается с кассы, `checkout-points-promo.html`) требует и проверяет `token`, email берётся только из него — приём самого заказа (весь остальной код файла) по-прежнему получает email прямо от Tilda как есть, это server-to-server вызов от платёжной системы, а не от браузера клиента, токена там нет и не нужно
- `supabase/migrations/20260903000000_recipients.sql` — таблица `recipients` и связь с `personal_dates`
- `supabase/migrations/20260922010000_newsletter_subscribers.sql` — таблица `newsletter_subscribers` (soft opt-in из заказов, статус/токен отписки) + RPC `unsubscribe_newsletter`, читает `newsletter-unsubscribe.html`
- `supabase/migrations/20260921040000_shop_closed_slots.sql` — таблица `shop_closed_slots` (закрытые интервалы доставки на конкретную дату), читает `checkout-slot-blocker.html`, пишет кабинет менеджера (`web/src/app/dashboard/shop/page.tsx`, вкладка "Режим работы")

Авторизация клиента везде одна и та же: `lk_auth_token` в `localStorage`
(HMAC-токен на 60 дней, выдаётся через email+одноразовый код, функция
`auth-verify`). Токен общий на весь домен — где бы ни стоял виджет, он
работает после одного подтверждения.

**Важный нюанс безопасности**, учтённый в каждом из этих файлов: перед
использованием токена клиент сверяет email внутри токена с тем, кто
реально сейчас залогинен через `tilda_members_profile` (родной Tilda
Members). При несовпадении — токен стирается. Без этой проверки на общем
устройстве один человек мог увидеть данные (включая телефон и адрес)
другого, если раньше на этом же устройстве подтверждал код кто-то ещё.
Если добавляете новый виджет с таким же `getAuthToken()` — переносите и
эту проверку тоже, не только сам токен.
